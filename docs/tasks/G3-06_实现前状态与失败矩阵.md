# G3-06 实现前状态与失败矩阵

状态：实现前冻结记录

范围：single-writer、SQLite-native backup、migration gate、physical corruption recovery、interrupted write

基线：`628b4fbc825d122a23c0a3fc9b2f8f36ebd9272d`

## 记号与共同不变量

- `W`：当前进程持有 sibling coordination SQLite 的进程生命周期写锁；`-`：未持有。
- `C`：current gameplay DB；`L/P/S`：latest/previous/staging backup；`Q`：quarantine；`R`：replacement staging。
- `V/I/M/-`：已验证有效 / 无效 / 缺失 / 不适用。`H/K/U`：current 物理健康 / 物理损坏 / unsupported newer schema。
- durable truth 一栏按 `Game/head/World/Conversation/Save/Recovery` 顺序描述；“整代”表示六类事实来自同一已提交数据库代，不混合 backup generations。
- 所有错误路径都必须 fail-loud；除明确 first-run 外禁止新建空 Game。`C` 是唯一 live authoritative truth，backup/quarantine/staging 永不成为并行 live truth。
- 每行风险结论依次为 `half-write / silent fallback / backup destruction / wrong-version downgrade / double writer`；除特别标注外目标均为 `否/否/否/否/否`。

## 6. 编码冻结结论

1. 启动顺序固定为：获得 coordination live lock → 检查 current path/artifacts → 物理分类 → schema 读取 → 必要时 verified pre-migration backup → persistence open/migration → logical/current-state validation → 缺 backup 时建立首份 verified backup → READY。
2. online backup 固定使用 vendored `SQLite.backup_to(path)`；灾难恢复先用 `SQLite.restore_from(backup_path)` 构建独立 replacement staging，再完整验证并发布。不得 ordinary-copy open WAL DB。
3. 发布始终保留至少一份已验证 recovery copy；staging 只有验证通过后才能进入 slot/current。任何 missing current 只要伴随 backup/quarantine/staging/recovery artifact，就不是 first-run。
4. Save COMMIT 与 physical backup refresh 是两个结果：前者成功、后者失败时保留 Save 成功并返回准确告警。close refresh 同样不得摧毁旧 backup。
5. UI 只请求/投影 `already_running`、physical corruption、可用 backup、confirmation、reopen-required；不直接操作 SQLite/path，不提供 browser/history。
