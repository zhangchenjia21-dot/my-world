# my world｜DSH 测试经验继承与跨阶段要求

## 0. 使用方式

这份文件既供负责 `my world` 的 AI / Agent 使用，也供项目维护者阅读。

它不是当前阶段的 Task Packet，也不授权提前实现未来阶段；它是一份**跨阶段产品与架构约束**，用于避免新项目重复 The World / DSH 长局已经暴露的问题。

当前实现任务、阶段和权威来源仍以以下内容为准：

- 用户当前明确指令；
- `AGENTS.md`；
- Vibe-Coding 中 `my world` 的当前产品规格 / 路线图；
- 当前代码与测试。

但当工作触及持久化、时间线（Timeline）、World Pack、NPC、势力（Faction）、GM 运行时、世界演化、上下文（Context）、存档 / 恢复、RPG UI、长局性能或 Alpha UAT 时，必须检查本文件。

本文面向人阅读的叙述以中文为主；文件名、Task ID、测试 ID、API、代码标识符和少量需要保持稳定的技术术语保留英文。

总原则：

> **迁移经验，不迁移宿主债务。**

---

# 1. 必须保护的核心玩家价值

`my world` 的工程成功不能以牺牲 DSH 已经验证的体验为代价。

必须保护：

- 优秀 AI GM 的文本质量与临场创造力；
- 玩家使用自然语言自由行动；
- 长期持续的本局现实（game-local reality）；
- NPC、势力、地点、关系、承诺与后果持续存在；
- 世界知识边界；
- 失败产生新的可玩处境，而不是把游戏关死；
- 主角授权边界；
- 世界时间可以压缩推进，但遇到有意义选择必须停下；
- Save / Restore 真正回到同一条时间线；
- RPG UI、地图、立绘、场景等用于增强游戏体验，而不是成为第二份状态源。

核心体验基线不是“代码能运行”，而是：

> **使用同一优秀模型时，`my world` 的 RPG 体验不能长期明显弱于 The World / DSH 或简单对话基线。**

# 2. 跨阶段不变量

## INV-DSH-01｜源资料（Source）只定义起点，不预写未来

World Pack / Source 可以定义：

- T0 之前的历史；
- 世界规则；
- 人物初始身份与关系；
- 地理、制度、文化；
- 历史惯性与参考资料。

T0 之后：

> **本局现实高于 Source 的默认历史轨迹。**

未来历史不能充当事件调度器。

禁止把“历史上某年会发生什么”长期作为一份活跃的“下一事件清单”塞进 GM 当前上下文。

## INV-DSH-02｜史料提供惯性，行动者创造历史

> **史料提供惯性，行动者创造历史。**

重大结果必须根据当前世界里的行动者（Actor）、势力、资源、制度、信息、地理和事件重新推出。

## INV-DSH-03｜玩家不是唯一的历史创造源

> **玩家可以改变历史，但不是唯一创造历史的人。**

系统必须防止 **主角因果垄断（Protagonist Causal Monopoly）**：

```text
错误状态：
Source 推进历史
+
玩家改变历史
+
NPC 只回应玩家

目标状态：
玩家 / NPC / 势力 / 制度 / 资源
互相作用
→ 产生新的历史
```

## INV-DSH-04｜离屏不等于停止行动

> **离开镜头，不等于停止行动。**

重要 Actor / Faction 在玩家不接触时仍可以推进自己的目标。

但这不要求全世界逐 tick 模拟。

## INV-DSH-05｜持久化不等于全量模拟

不要实现“每个 NPC 每回合都跑一次模型”。

世界演化应根据以下因素选择性运行：

- 时间推进；
- 重大事件；
- 当前高影响 Actor / Faction / Front；
- 与玩家和世界的因果相关性。

## INV-DSH-06｜骰子决定不确定性，不抹除人物

> **骰子决定不确定性，不抹除人物。**

人物底线、已经成立的事实和物理不可能，不能因为一次高骰自动失效。

## INV-DSH-07｜有意义的选择要有不同风险结构

不要让不同方案只是换一段文案，最后都变成同一个 `d20 vs DC15`。

风险至少可以在以下维度产生真实差异：

- 是否需要检定；
- DC；
- 优势 / 普通 / 劣势；
- 失败代价；
- 暴露、资源、时间、关系、身份、伤害和局势升级。

## INV-DSH-08｜UI 只投影真相

> **UI 是游戏权威状态的投影，不是第二份真相。**

地图、人物、关系、任务、机制、物品 UI 都不能自行拥有另一份权威 gameplay state。

## INV-DSH-09｜模型生成候选，程序提交现实

> **模型生成候选，程序提交现实。**

模型适合：

- 理解玩家自由语言；
- 生成 NPC / 世界行动候选；
- 叙事；
- 语义判断；
- 开放内容创作。

程序 / Domain Owner 负责：

- 身份（identity）；
- 权限 / ownership；
- RNG；
- 权威状态变更（authoritative mutation）；
- 原子持久化；
- Save / Restore；
- 时间线；
- 结构与约束。

但不能因此提前制造 Universal Schema / Universal ECS。

# 3. G1｜基础阶段需要保留的注意事项

G1 当前仍是 Foundation Spike，不因为本文件而扩大范围。

与 DSH 经验相关的要求只有：

- AI 流式输出必须不冻结 UI；
- Cancel / Error 必须有可恢复状态；
- 中文长文本是核心交互面，不是附加测试；
- 本地 IO、图片资产和 Windows Export 必须在真实环境可用；
- Provider 接入保持窄，不提前制造通用 AI 平台；
- G1-06 决定 Runtime 边界时，必须考虑 G3 / G5 / G7 的长期需要，而不能只看短 Demo 哪种写法最省事。

特别注意：

> DSH 后期最明显的问题之一，就是长局上下文和文件维护越来越慢。

因此，如果某个 G1 架构选择明显会迫使未来把全部长期世界状态绑在 UI Node / Scene Tree / 无界 transcript 上，应在 G1-06 将它明确记录为风险。

# 4. G2｜AI 对话主干

G2 不只是“聊天框能调用模型”。

必须保护：

- 自然语言玩家输入；
- 高质量 GM 流式输出；
- 玩家可以在 GM 输出后立即继续；
- Cancel / Retry 不制造隐藏的重复 Turn；
- Conversation 是表现和 Context 来源之一，但不等于权威 World State；
- 后台状态维护不得挡在叙事前面。

正式 UX 原则：

> **叙事优先；后台工作应尽量在玩家阅读时进行。**

不要为了追求后台一致性，让玩家每回合都先等待一大段维护工作，之后才看到故事。

G2-GATE 至少应做一次同模型基线比较：

```text
my world 的 GM 输出
vs
简单模型聊天 / DSH 参考实现
```

如果工程更稳定，但实际体验明显更无聊、更拘谨、更机械，应判定为产品风险，而不是简单归为“以后再润色”。

# 5. G3｜持久游戏与时间线

这是 DSH 经验中最需要重新设计的一层。

## G3-REQ-01｜权威状态必须即时提交

不要复制：

```text
DELTAS
→ 等 N 回合
→ 模型 consolidation
→ 批量编辑 Owner Markdown
```

目标：

```text
世界发生持久变更
↓
一次可靠提交
↓
权威状态立即成立
↓
UI / Context / Save 从同一事实派生
```

允许使用 Event Log、Snapshot、数据库、Projection 等不同实现，但具体技术方案应由 G3 的真实纵向验证决定。

## G3-REQ-02｜Timeline 是一级领域概念

从第一版就区分：

- Game；
- Timeline；
- Save Point；
- World State；
- Agent Context；
- Conversation History。

不要再次让宿主 Session 代理 RPG Timeline。

## G3-REQ-03｜Restore 后必须隔离未来记忆

必须有产品测试：

```text
在 T2 存档
→ 玩到 T5
→ 恢复到 T2
→ 继续游玩
```

PASS 条件：

- World = T2；
- Context = T2 时点可以合理知道的信息；
- T3–T5 的未来不能继续影响模型；
- UI 不残留未来状态。

## G3-REQ-04｜存档身份不能歧义

玩家展示名称必须与内部 identity 分离。

不能出现两个存档共用同一个 storage key，然后系统“取第一个”的情况。

## G3-REQ-05｜恢复材料与玩家存档分离

Crash 恢复、Restore 前保护点等 recovery material 不应污染普通 Save 列表。

---

# 6. G4｜World Pack 与本地内容基础

## G4-REQ-01｜Source / 本局实例 / Runtime State 必须分层

World Pack 是可复用的 Source。

一局开始后必须形成独立的本局现实。

Source 更新默认不能重写旧游戏中已经发生的事实。

## G4-REQ-02｜未来史料不能成为主动脚本

历史世界可以携带：

- T0 前事实；
- 史料；
- 人物参考；
- 典型趋势；
- 原历史轨迹作为参考。

但 Runtime 不应持续把“未来几年将发生 X / Y / Z”作为活跃上下文。

历史参照应按需检索，不能成为自动事件队列。

## G4-REQ-03｜美术资产是一等 World Pack 能力

首代至少考虑：

- 角色立绘（portrait）；
- 场景图（scene art）；
- 地图（map）；
- 世界专属 UI / 展示元数据。

地图首代保持**作者提供为主（authored-first）**：

> **World Pack 作者提供专属地图，通用客户端负责展示、缩放、拖动和当前位置投影。**

不要在 G4 提前实现自动地图生成、GIS、寻路或统一世界坐标引擎。

---

# 7. G5｜世界语义与 GM Runtime —— DSH 最大教训的落地点

G5 不能只做到“NPC 会说不同的话”。

G5 必须证明：

> **世界在没有玩家直接推动时，也能创造新的、合理的历史。**

## G5-REQ-01｜行动者自主性

重要 NPC 至少要能维持语义上等价于以下内容：

```text
Current Agenda（当前议程）
Fear / Cost（恐惧 / 代价）
Red Line（红线）
Obligation（义务）
Independent Next Move（独立的下一步行动）
```

不要求统一 JSON Schema；但 Runtime 必须能回答：

> 玩家暂时不理这个人，他自己准备做什么？

## G5-REQ-02｜势力 / 组织自主性

诸侯、政权、组织、家族、军队、商会等不能只是 NPC 外壳。

高影响 Faction 至少需要：

- 当前战略目标；
- 资源 / 约束；
- 已知威胁；
- 外交 / 内部矛盾；
- 可以采取的下一步。

## G5-REQ-03｜世界演化

实现一个**事件驱动、优先级驱动**的世界演化过程，而不是全世界逐 tick 运转。

概念流程：

```text
时间推进 / 重大变化
↓
选出当前值得模拟的 Actor / Faction / Front
↓
读取其目标 / 认知 / 资源 / 关系 / 义务 / 威胁
↓
形成各自行动
↓
行动互相碰撞
↓
产生世界事件 / 持久状态变更
↓
GM 再选择哪些内容进入玩家视野
```

具体 Planner / Resolver / Commit 边界由 G5 架构设计决定，不要在 G1–G4 提前写死。

## G5-REQ-04｜反事实传播

关键事实发生改变时，不能只更新一张人物卡。

必须识别受影响者并传播：

```text
关键事实改变
↓
谁在意 / 谁知道 / 谁受益 / 谁受威胁
↓
认知与计划发生变化
↓
产生新的行动
```

典型 DSH 失败案例：

- 卢植没有按原历史失势；
- 皇甫嵩全胜并长期掌权；
- 但 189 年的政局仍然大体按原历史时间表推进。

未来 PASS 标准不是“历史改变后玩家一定赢”，而是：

> **原历史结果即使仍然发生，也必须是在改变后的棋盘上重新通过因果推出。**

## G5-REQ-05｜自适应阻力

世界难度不能主要依靠机械提高 DC。

强玩家应该自然导致：

- 对手重新结盟；
- 中立者提高防范；
- 下属之间产生利益冲突；
- 好友可能因为底线反对；
- 制度性阻力；
- 资源竞争；
- 信息战与误判。

“世界反抗玩家”的真正含义是：

> **世界有自己的目标，而不是专门惩罚玩家。**

有时世界中的行动者也会在玩家不在场时主动帮助玩家。

## G5-REQ-06｜NPC 人格必须进入风险与决策

同一种沟通方式，对不同人物应产生不同风险。

例如：

- 重视证据的人，可能因为证据充分而获得优势；
- 重视名分的人，可能因为方案越线而直接拒绝；
- 好大功的人，可能被荣耀 / 风险收益打动；
- 直率人物可能厌恶复杂话术。

人物差异必须影响：

- 是否可行；
- 优势 / 劣势；
- DC；
- 失败代价；
- 后续关系。

## G5-REQ-07｜知识来源继续严格

自主行动不能变成全知 AI。

Actor 做计划前只能使用其在世界内合法知道的信息。

世界演化中的每个重要行动，都要能解释：

> 这个人为什么知道？为什么现在做？为什么有能力做？

# 8. G5 必须加入的三项核心产品测试

## TEST-WORLD-01｜玩家缺席测试

把玩家放在偏远地点，或让玩家一年不干预主线政治。

PASS：

- 世界发生来自 NPC / Faction 的新变化；
- 这些变化可以由当前目标和条件解释；
- 不是简单播放 Source 的未来时间线。

FAIL：

- 天下除了历史脚本外几乎不动；
- 所有关键事件都等待玩家触发；
- 世界变化只发生在玩家附近。

## TEST-WORLD-02｜反事实传播测试

人工建立一个明显偏离 Source 的关键前提。

例如：

```text
重量级政治人物没有失势
关键战争结果被改写
一个原本弱小势力提前变强
```

然后让玩家数年不参与相关区域。

PASS：其它 Actor / Faction 的战略产生可以解释的新分叉。

FAIL：原历史节点仍然按时间表逐一发生，只是替换了几个角色或措辞。

## TEST-WORLD-03｜独立行动者测试

选择重要 NPC A。

先记录：

> 如果玩家一年不与 A 接触，A 当前准备做什么？

随后推进世界。

PASS：A 大体按照自己的目标行动，或因为中途出现新的世界事实而合理改变计划。

FAIL：A 原地等待玩家，或突然按照 Source 未来史实行动，却没有当前动机链。

# 9. G6｜RPG 体验与 2D 表现

DSH 已经证明 RPG UI 有价值，但 UI 不应替代世界语义。

G6 的优先级仍应由玩家真实需要驱动。

核心交互面包括：

- 叙事（Narrative）；
- 角色立绘；
- 场景图；
- 地图；
- 人物 / 关系 / Thread / Mechanic / Inventory 等状态 UI。

地图首版只需要：

```text
作者提供的地图资产
+
地点映射
+
玩家当前位置标记
+
缩放 / 拖动
```

不提前做：

- 点击地图自动移动；
- 路径规划；
- GIS；
- 自动 POI；
- 动态势力边界；
- 自动地图生成。

只有真实试玩出现需求后再扩展。

# 10. G7｜长局上下文与性能

这是退出 DSH 宿主的直接原因之一，必须成为正式 Gate。

## G7-REQ-01｜Context 不能随世界历史无界增长

必须区分：

```text
完整世界状态
!= 当前相关状态
!= 模型工作上下文
```

Context Assembly 只应给当前任务足够的信息。

## G7-REQ-02｜Transcript 不是长期世界数据库

完整聊天历史不能成为唯一长期记忆。

系统需要可恢复的：

- 权威事实；
- 最近场景 / 叙事连续性；
- 当前相关 Actor 状态；
- 活跃 Front / Thread；
- 知识边界。

## G7-REQ-03｜不要重新发明“大 consolidation”

允许后台压缩（compaction）或 Projection 重建，但不能让系统长期依赖：

> 每 N 回合让模型重新读取大量状态并批量修正文档。

## G7-REQ-04｜长局必须真实压测

至少建立跨多年 / 多势力 / 多人物的长局测试。

记录：

- Context token / 字符数；
- GM 首 token 延迟；
- 完整生成耗时；
- 状态提交延迟；
- Save / Restore 延迟；
- 内存占用；
- UI 响应性。

不能只凭 20 回合 Demo 宣布 G7 PASS。

---

# 11. G8｜Mod / 创作生态

World Pack / Mod 是一级能力。

必须保留：

- Source 与运行中的本局隔离；
- World Pack 可以携带地图、立绘、场景、Source Lore、初始人物和可选机制；
- 本局现实不能反向污染 Source；
- Source 升级对旧游戏的影响必须显式；
- 作者不需要理解底层 Runtime 数据库，就能创作普通世界内容。

不要因为 Mod 需求，提前暴露所有内部 Domain 类型，或允许任意脚本获得权威写权限。

---

# 12. G9｜独立版 Alpha / 发布验证

G9 不能只看工程稳定性。

最终 Alpha 至少同时验证以下两类内容。

## 工程验收

- 安装 / 启动；
- Provider；
- 本地持久化；
- Save / Restore；
- 无明显数据损坏；
- 长局性能；
- Crash / recovery；
- World Pack 安装与加载。

## 产品价值验收

- 使用同一模型时，GM 质量不明显弱于 DSH / 简单基线；
- 玩家自然语言自由度成立；
- NPC 有明显不同的自主性；
- 世界在玩家离屏时继续演化；
- 反事实改变能够传播；
- 历史世界不会退化为时间表播放器；
- 玩家成功会产生合理的新政治 / 社会 / 人物难度，而不是只发生数值膨胀；
- 长期游玩仍有沉浸感；
- UI / 美术增强体验，但不会压过对话式 RPG 主循环。

Alpha 的最终产品价值 PASS 必须由真实 Owner / 玩家通过长局体验裁定。

# 13. 明确不要带进 my world 的 DSH 实现

不要复制：

- DSH Session workaround；
- Restore 后新建 DSH Session 的恢复 seam；
- `fs.watch` Restore workaround；
- DSH Plugin Lifecycle；
- 周期性模型 consolidation 作为主要状态一致性机制；
- DELTAS + 批量 Markdown edit Runtime；
- Markdown 默认充当权威 gameplay DB；
- 通用 Agent Workspace 的目录结构直接决定 Player UI；
- Active Context 长期携带 Source future event checklist；
- “玩家改变、NPC 回应、历史继续播放”的主角因果垄断模式。

可以继承的是这些 workaround 背后暴露出的需求，而不是实现本身。

# 14. 负责项目的 AI 每次做相关设计时应自问

当任务涉及 G3–G9，至少检查：

1. 这个设计是在解决已经观察到的真实问题，还是只因为理论上“可能需要”？
2. 它是否保护 GM 输出质量和玩家自由度？
3. 权威真相在哪里？是否产生了第二份真相？
4. Save / Restore 是否同时恢复 Timeline 和 Agent Context？
5. Source 是参考资料，还是偷偷变成了剧本？
6. 玩家不干预时，重要 Actor / Faction 会不会自己行动？
7. 一个已经改变的事实，能否影响远方与它存在利益关系的人？
8. NPC 是否只有台词差异，还是目标、底线和行动真正不同？
9. 难度来自世界因果，还是机械提高 DC？
10. 当前 Context 是否只包含真正相关的信息？
11. 这个系统是否会在 5 年长局后明显变慢？
12. 是否正在把 Godot / Provider / Database 的技术概念误当成产品 Domain 语义？

如果这些问题没有答案，不要因为代码已经能跑，就宣布相关 Stage 的产品目标完成。

# 15. 最终提醒

The World / DSH 已经证明：

> **持久世界是必要的。**

长局后期又进一步证明：

> **持久世界不等于自主演化世界。**

`my world` 下一代真正需要跨过去的，是这一条。

最终目标不是做一个“记忆更好的聊天 RPG”，而是：

> **做一个会自己产生历史的世界；AI GM 把其中最有意义的部分组织成玩家正在经历的故事。**
